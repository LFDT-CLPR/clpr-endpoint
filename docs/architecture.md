# Architecture

Prerequisite: read `docs/README.md` and the two spec docs it references.

## Module layout

Seven Gradle subprojects, each one Java module under `org.hiero.clpr.relay.<suffix>`:

|          Module          |    Suffix     |                                                                                                                                                                  Role                                                                                                                                                                  |
|--------------------------|---------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `clpr-relay-proto`       | `proto`       | `.proto` files + PBJ-generated types for the gRPC sync protocol and on-chain state shapes. Spec §1 defines the wire forms.                                                                                                                                                                                                             |
| `clpr-relay-core`        | `core`        | Pure interfaces and value types: `ClprChannelOps`, `ChannelLookup`, `InboundBundleQueue`, `ContractStateReader`, `BundlePayloadCodec`, `BundleTrimmer`, `BundleConstructor`, `BundleRequestConstructor`, `PeerEndpointCache`, `CommitmentLevel`, `ParsedBundle`. No I/O.                                                               |
| `clpr-relay-evm`         | `evm`         | The only ledger-aware module. Implements `ContractStateReader` and the per-format `BundleConstructor` / `BundlePayloadCodec` (QBFT, Sei/CometBFT, Ethereum-PoS) against an EVM JSON-RPC node — plus a beacon (consensus-layer) node for Ethereum PoS. ABI codec, ECDSA signer, and the serial `AccountTransactionSubmitter` live here. |
| `clpr-relay-grpc-server` | `grpc.server` | Helidon-hosted PBJ gRPC server (`ClprGrpcServer`, `ClprSyncService`). Implements the two-phase bidi-streaming `sync` RPC via a per-stream `ClprSyncSession` (built by `ClprSyncHandler`). Hosts `ThrottleEnforcer` (inbound bundle limits).                                                                                            |
| `clpr-relay-grpc-client` | `grpc.client` | Outbound peer client (`ClprEndpointClient`). Wraps the gRPC stub used by `sync` to call remote endpoints.                                                                                                                                                                                                                              |
| `clpr-relay-sync`        | `sync`        | Orchestration: per-channel sync loops, peer selection. No JSON-RPC or gRPC wire details — depends on `core` abstractions and `grpc-client` for outbound peer calls.                                                                                                                                                                    |
| `clpr-relay-app`         | `app`         | Entry point, YAML config loader, dependency wiring, Prometheus metrics endpoint.                                                                                                                                                                                                                                                       |

Dependency direction: `app → {sync → grpc-client, grpc-server, evm} → core → proto`. `sync` depends on `grpc-client` for outbound peer calls; `grpc-client` and `grpc-server` do not depend on each other.

## Entry point and wiring

- `clpr-relay-app/.../ClprRelayMain.java` — main method. Loads config, builds metrics, calls `RelayInstance.build(config, metrics)`, starts metrics HTTP server, calls `relay.start()`.
- `clpr-relay-app/.../RelayInstance.java` — explicit constructor wiring, no DI framework. Builds a three-tier hierarchy that mirrors the config: a `LocalNetworkAdapter` per `localNetworks[]` entry (shared JSON-RPC client + gas strategy + CometBFT client), a `ClprServiceHandler` per `clprServices[]` entry (owns its `ChannelDiscoveryTask` and its channel handlers), and a `ClprChannelHandler` per channel (owns that channel's `EvmContractStateReader`, the network's shared per-account `AccountTransactionSubmitter`, a `BundleConstructor` + `BundleRequestConstructor`, `LedgerConfigurationPayloadProvider`, `PeerEndpointCache`, `ThrottleEnforcer`, inbound codec, and the two worker loops it spawns). The relay-global pieces are the gRPC server (`ClprGrpcServer` + `ClprSyncHandler`), the peer client (`ClprEndpointClient`), and the metrics registry. `ClprChannelHandler` implements `ClprChannelOps`, so the inbound gRPC paths reach channel-scoped state through a `ChannelLookup` that finds the handler by id across every `ClprServiceHandler` (this replaced the old per-interface `ChannelMapped*` resolver adapters).

`start()` starts the gRPC server, then each `ClprServiceHandler` (which registers its predefined channels and launches discovery); each `ClprChannelHandler` spawns its own sync + manifest-refresh virtual threads. `stop()` is invoked from a JVM shutdown hook and tears the hierarchy down.

## Key abstractions (read these signatures first when navigating code)

All in `clpr-relay-core/.../`:

|----------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `ClprChannelOps`           | The per-channel surface the gRPC glue consumes, implemented by `ClprChannelHandler`: `channelId()`, `bundleConstructor()`, `bundleRequestConstructor()`, `inboundBundleQueue()`, `contractStateReader()`. `ChannelLookup.findById(channelId) → Optional<ClprChannelOps>` resolves the right one for an inbound stream across every `ClprServiceHandler` (it replaced the old `ChannelMapped*` per-interface resolver adapters).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `InboundBundleQueue`       | `offer(Bytes rawBundleBytes, @Nullable ClprEndpoint peer) → void`. Hands a peer's bundle payload to the channel's inbound path; the `ClprChannelHandler` impl parses it (`BundlePayloadCodec`, replay-trimmed against the local `receivedMessageId`), gates it on the `ThrottleEnforcer`, and enqueues on the signing account's serial `AccountTransactionSubmitter`. The outcome (skip/submit/revert/fail) is surfaced through metrics, never returned or thrown.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `BundleRequestConstructor` | `createBundleRequest() → BundleRequest`. Builds the phase-1 request from local channel state: the next message id we want, our status, our verifier's trust anchor id, and the manifest version we hold of the peer.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `ContractStateReader`      | Reads `ClprChannel`, `ClprLedgerConfiguration`, the endpoint manifest, and individual queued messages at a chosen `CommitmentLevel` / block tag.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `CommitmentLevel`          | `LATEST` / `SAFE` / `FINALIZED`. Maps directly to EVM block tags. Per-channel in config.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `BundleConstructor`        | Build a bundle **ad hoc** from a peer's `BundleRequest` (`createBundle(channelId, request)` → `BundleWithConstructionMetadata`, the payload plus the `constructedAtHeight` it was proven against): sender-trims messages from `request.fromMessageId`, drives trust-anchor catch-up from `request.currentTrustAnchorId`, and attaches a manifest proof when local > `request.currentEndpointManifestVersion`. `QbftBundleConstructor` / `SeiBundleConstructor` / `EthereumPosBundleConstructor` (real proofs) and `StubBundleConstructor` (CLPRSTUB test format); the `CachedBundleConstructor` decorator (wired in `ClprChannelHandler`) memoizes results in a bounded LRU `BundleCache` keyed by `(channelId, request, probedChainHeight)` — the height read once per call for both lookup and store, **not** the delegate's `constructedAtHeight` (an independent read that can differ mid-build). Skipped for constructors that report no numeric height (`Stub`, `EthereumPOS`).                                                                                               |
| `BundlePayloadCodec`       | Decode an inbound peer bundle into queue metadata + messages via `decodeBundle(bytes)` (no client-side crypto — the proof is verified on chain). `parseBundle(bytes, receivedMessageId)` additionally drops messages the local ledger has already accepted and re-encodes the proof, so an already-delivered message can't sink the bundle as a replay; the chain-agnostic message selection lives in `BundleTrimmer`, the format-specific re-encode in the codec. Re-encoding is skipped (bytes returned verbatim) when nothing is trimmed. Implemented by `QbftProofCodec` / `SeiProofCodec` (trimming) and `HieroProofCodec` / `EthereumPosProofCodec` / `StubProofCodec` (verbatim — re-encoding a block-stream StateProof or a sync-committee/light-client proof is out of scope). A codec instance is **bound to one channel** (its channelId is supplied at construction): built per-channel by `ClprChannelHandler`, used inside that channel's `inboundBundleQueue()` impl; the inbound server reaches it by resolving the channel's `ClprChannelOps` via `ChannelLookup`. |
| `PeerEndpointCache`        | In-memory map of `accountId → ClprEndpoint`. Seeded from the on-chain per-Channel peer roster when the `ClprChannelHandler` is built and replaced wholesale by the channel's `EndpointManifestRefreshTask` when the peer endpoint manifest's `version` advances (spec §2.4.2). Reads observe atomic snapshots.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `FailState`                | Pure two-state (`HEALTHY ↔ FAILING`) failure machine for the per-channel loops: streak-driven capped backoff + full-then-compact log decision. No IO, no clock. Owned by each loop task.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |

## Data flow

Sync is a **two-phase pull**: bundles are built ad hoc from a peer's `BundleRequest` (`BundleConstructor.createBundle`), not on a state-change trigger. See `sync-protocol.md` for the full three-message exchange.

### Outbound (we initiate — pull our peer's data and push ours)

1. `ChannelSyncTask` (a virtual thread per channel) reads `getChannel(channelId)` and picks a peer (`PeerSelector`).
2. It sends **phase 1**: `ClprSyncPayload{channelId, bundleRequest}` (what we want next, our status/trust-anchor, and the manifest version we hold of the peer) via `ClprEndpointClient.sync`.
3. The peer replies with a `bundleResponse` answering our request plus its own `bundleRequest`. We hand its response to `inboundBundleQueue().offer` the moment it arrives (decoupled from our outbound leg) and answer its request in **phase 2** with our own `createBundle`.

### Inbound (peer initiates — we respond)

1. The peer's `sync` stream lands on `ClprSyncService` → `ClprSyncHandler.newSession` → a per-stream `ClprSyncSession`.
2. **Phase 1**: the session builds `createBundle(channelId, peerRequest)` and attaches our own `bundleRequest`, replying once.
3. **Phase 2**: it hands the peer's `bundleResponse` to the channel's `inboundBundleQueue().offer`, which decodes it into a `ParsedBundle` (`BundlePayloadCodec`, replay-trimmed), gates it on the channel throttle, and enqueues via `AccountTransactionSubmitter.submit`.
4. The submitter ABI-encodes `submitBundle(channelId32, payload)`, signs the EVM tx client-side as EIP-1559 (type-2), and submits via `eth_sendRawTransaction`, polling the receipt until mined or timeout.

## Threading model

- Each `ClprChannelHandler` owns its own two virtual threads and holds a handle to each: one `ChannelSyncTask` (sync loop, started only when `StartOptions.outboundSync()` is true) and one `EndpointManifestRefreshTask` (peer-manifest refresh poller, always started). The handler spawns both in `start(outboundSync)` — tagging each thread's log context with the channel id — and signals both to stop in `stop()`. Each task captures its own thread when `run()` starts; `stop()` flips the task's flag and self-interrupts that thread, so a blocking poll/backoff sleep wakes promptly. There is no central `SyncOrchestrator` / `EvmStateChangeListener` orchestrating threads across channels; the handler is the sole owner (the aggregate loop-failure gauges are registered once by `RelayInstance`, computed at scrape time from every live handler's `FailState`).
- On `CLOSED`, the sync task self-stops instead of polling the dead channel forever; the manifest-refresh task keeps running until the handler stops it (it reads only the peer manifest, so it has no channel status to self-stop on — a closed channel's manifest simply stops changing). The handler remains registered in its `ClprServiceHandler` (which also keeps discovery from re-registering an already-known — including already-closed — channel).
- Each `ClprServiceHandler` keeps **at most one channel handler per channel id**: `addChannel` ignores (and logs) a duplicate registration, so the predefined-registration and discovery paths cannot double-wire a channel.
- **Both loops are failure-resilient.** Neither `ChannelSyncTask.run()` nor `EndpointManifestRefreshTask.run()` can die on an unchecked per-iteration exception. Each task owns a `FailState` (in `core`) — a pure two-state machine (`HEALTHY ↔ FAILING`) that, on each failure, advances an episode-wide streak, returns a **capped, exponentially-growing backoff** (base and cap from `relay.backoff`, default 1 s → 30 s — never the tight cadence), and decides logging: the **first occurrence of each fault fingerprint** logs at ERROR with the full stacktrace, **repeats** log a compact ERROR line (`#streak` + `channelId` + fingerprint). The **first clean iteration** resets the streak (and fingerprint set) in one step and logs a single recovery INFO. The backoff is an interruptible `Thread.sleep`, so a `stop()` interrupt wakes the task mid-backoff. Peer-RPC failures inside `executeSyncCycle` stay **peer-scoped** (handled by `PeerStats` backoff) and never escalate the whole channel. Backoff bounds are configured by `relay.backoff.{baseMs,capMs}`.
- Helidon's WebServer for inbound gRPC.
- All shared state (`PeerEndpointCache`, and the per-account `AccountTransactionSubmitter` bounded queue drained by a single worker thread) is protected by explicit locks or concurrent collections — there is no global event loop.

| `AccountTransactionSubmitter` | `evm`         | Per-`(network, signing account)` serial submitter (in `clpr-relay-evm` — it needs the JSON-RPC client). A single worker virtual thread drains **bounded per-channel FIFO queues round-robin** (one request per channel per turn, so no channel starves another), driving each request to a definite outcome before the next, so at most one transaction per account is in flight — which is why it needs no nonce tracking (it reads a fresh `latest` nonce once per request). Gates every paid submission on a gas-free `eth_call` of `submitBundle` run at send time (always on): a revert → skip (`sync.bundle.skipped{reason=rejected}`). That preview is also the true duplicate gate — a stale bundle the pull (`ChannelSyncTask`) and push (`ClprSyncHandler`) paths would both deliver reverts (it is previewed only after the first has mined, since the worker is serial). As queue hygiene, an exact-bundle-bytes re-offer already pending for a channel is suppressed at enqueue (`evm.tx.queue_deduped`) so those two paths cannot fill the FIFO with identical copies and drop a genuinely-new bundle; this is content-exact, so unlike the removed counter-keyed fingerprint it never suppresses a distinct PAUSE-recovery bundle. Only an empty **ACTIVE** initial-state bundle is dropped without a preview (`sync.bundle.skipped{reason=empty}`) — a status-only close at those same counters is not empty and is always submitted so the lifecycle advances. No coalescing (order preserved per channel); a full per-channel queue drops that channel's new request (`evm.tx.queue_dropped`) without affecting others. The chain is the sole arbiter, so a transient failure is retried at the same nonce (each round re-reading the live market fee and re-pricing up if it rose, clamped to the cap, to clear a base-fee spike); a request that never reaches a verdict is abandoned after a `MAX_SUBMIT_ROUNDS` safety valve (`evm.tx.failures{reason=abandoned}`) so one stuck bundle cannot wedge the worker — the sync loop re-drives it. |

## What is NOT here

- No verifier-contract integration. Proof construction/verification are stubs.
- No on-chain event subscriptions. Each channel's `EndpointManifestRefreshTask` polls.
- No persistent state. Everything is reconstructable from on-chain reads on restart; `PeerStats` etc. is in-memory only.
- No bundling/batching across channels. Each channel's task is independent.
